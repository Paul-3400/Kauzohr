## 🔍 Diagnose-Weg

### Schritt 1: Datenkette aus Handover 01.09. rekonstruiert

```
ESP32 ──HTTP POST──▶ receiver.py (Port 5000)
                      │ liest Header "X-Battery-Voltage"
                      │ kalibriert: V_echt = V_roh × 1.0548
                      │ schreibt → voltage_log.json
                      ▼
dashboard.py (Port 5001) liest voltage_log.json → zeigt Kacheln
```

Schlüssel-Erkenntnis: Die **Config-Werte** holt das Dashboard per HTTP vom Receiver (funktionierte), die **Batteriewerte** liest es direkt aus der Datei `voltage_log.json` (fehlgeschlagen). → Verdacht: Datei fehlt, leer oder veraltet.

### Schritt 2: Terminal-Diagnose auf dem Pi

```bash
ls -lt ~/BirdSongs/StreamData/ | head -5
ls -la ~/birdnet-receiver/voltage_log.json
tail -c 300 ~/birdnet-receiver/voltage_log.json
sudo journalctl -u birdnet_receiver -n 30 --no-pager
```

**Befunde:**

| Prüfung | Ergebnis | Schluss |
|---|---|---|
| WAV-Dateien | Frische Dateien von heute 10:17/10:18 | ✅ ESP32 sendet einwandfrei |
| voltage_log.json | Zuletzt geändert **14.09. 18:12**, 1 MB | ⚠️ Log seit 2 Tagen eingefroren |
| journalctl | `[WARNING] voltage_log.json Fehler: Unterminated string starting at: line 1 column ...` (alle ~30 Sek.) | 🎯 **JSON-Datei korrupt** |

Wichtig: receiver.py v1.4 hat einen Stille-Generator, der den RTSP-Stream auch ohne ESP32-Aktivität am Leben hält. «BirdNET läuft» beweist also nicht, dass der ESP32 sendet – deshalb wurde das zuerst geprüft.

---

## 🧩 Ursachenanalyse (Konfidenz: hoch)

**Kausalkette:**

1. **Bis 14.09. ~18:11:** Alles normal. receiver.py schreibt bei jedem Upload die Spannung in `voltage_log.json` – dazu wird die Datei komplett neu geschrieben (lesen → Eintrag anhängen → zurückschreiben).
2. **14.09. 18:12:** Datenträger 100% voll (Wochenputz existierte noch nicht). Der Schreibvorgang wird mitten im JSON abgebrochen → Datei abgeschnitten → ungültiges JSON («Unterminated string»).
3. **14.09. → 16.09.:** Bei jedem Upload versucht der Receiver, die Datei zu lesen → Parsing schlägt fehl → Fehler wird abgefangen (nur WARNING, kein Absturz) → **kein neuer Eintrag**.
4. **15.09.:** Wochenputz macht Speicher frei → WAVs und BirdNET-Go laufen wieder. Aber `voltage_log.json` bleibt korrupt – freier Speicher heilt keine beschädigte Datei.
5. **16.09. 10:28:** Reparatur (siehe unten) → Kette läuft wieder.

**Die eigentliche Lektion – zwei Fehlerarten:**

| Fehlerart | Beispiel | Verhalten |
|---|---|---|
| **Fail-loud** | BirdNET-Go beim vollen Speicher | Verweigert Dienst mit klarer Meldung → sofort sichtbar |
| **Fail-silent** | Voltage-Logging nach der Korruption | Läuft «normal» weiter, nur ohne Daten → 2 Tage unbemerkt |

Abgefangene Fehler verbergen Probleme: Der Receiver überlebte still, konnte aber nicht mehr anhängen (Henne-Ei: Datei nicht lesbar → nicht überschreibbar). Dashboard-Neustart hätte nichts gebracht – das Dashboard war nie das Problem.

## 🔧 Lösung

### Schritt 1: Sicherheitskopie

```bash
cd ~/birdnet-receiver
cp voltage_log.json voltage_log.json.kaputt
```

### Schritt 2: Datei reparieren (Python-Einmal-Skript)

```bash
python3 - << 'EOF'
import json

path = "voltage_log.json"
text = open(path).read()

try:
    data = json.loads(text)
    print("Datei ist bereits in Ordnung,", len(data), "Eintraege")
except json.JSONDecodeError:
    # Letzten vollstaendigen Eintrag finden und Array sauber schliessen
    idx = text.rfind("},")
    repaired = text[:idx+1] + "]" if idx > 0 else "[]"
    data = json.loads(repaired)
    with open(path, "w") as f:
        f.write(repaired)
    print("Repariert:", len(data), "Eintraege erhalten, letzter:", data[-1])
EOF
```

### Schritt 3: Kontrolle

```bash
sudo journalctl -u birdnet_receiver -f
```

→ Nach dem nächsten Upload (~30 Sek.) verschwand die WARNING, INFO-Meldungen normal. Kein Service-Neustart nötig: receiver.py liest die Datei bei jedem Upload neu (deshalb kam die WARNING ja im 30-Sekunden-Takt).

## 📉 Datenverlust

Spannungseinträge vom **14.09. 18:12 bis 16.09. 10:28** sind verloren – sie wurden nie geschrieben und sind nicht rekonstruierbar. Die Backup-Datei `voltage_log.json.kaputt` enthält den (unvollständigen) alten Stand vom 14.09. und kann bei Bedarf gelöscht werden.

---

## 🛡️ Entscheidung: Keine Robustheits-Patches

Zur Diskussion standen zwei Erweiterungen in receiver.py:

1. **Atomares Schreiben** (tmp-Datei + `os.replace()`) – verhindert Korruption beim Schreiben
2. **Selbstheilung** (bei Parse-Fehler: kaputte Datei sichern, neu beginnen)

**Entscheidung von Paul:** Beide verworfen – **Vertrauen auf die Vorbeugung** (Wochenputz-Cronjob vom 15.09. verhindert das Volllaufen des Speichers künftig). Falls es doch wieder schiefgeht, ist der Suchpfad bekannt: `journalctl -u birdnet_receiver` → WARNING «voltage_log.json» → Reparatur-Skript aus diesem Handover.

---

## 📚 Lessons Learned

1. **«Es läuft» ist nicht «es läuft vollständig»** – ein System kann still Daten verlieren, während alle sichtbaren Teile funktionieren.
2. **Abgefangene Fehler verbergen Probleme** – ein WARNING-Log, das niemand liest, ist keines.
3. **Volle Datenträger beschädigen Dateien bleibend** – freigemachter Speicher heilt keine Korruption.
4. **Ketten-Denken bei der Diagnose:** Config klappt (HTTP-Weg) + Werte fehlen (Datei-Weg) → Engpass ist die Datei, nicht der Service.
5. **Diagnose vor Aktion:** Dashboard-Neustart wäre wirkungslos gewesen; erst die WARNING im Journal zeigte den wahren Ort des Problems.
